# AgentGuard 当前产品方向

> 状态：Active
> 生效日期：2026-07-16
> 适用范围：产品、设计、研发、测试、开源运营

## 1. 当前阶段

AgentGuard 已完成 CLI MVP 的主要闭环，不再处于“验证能否做出 MVP”的阶段。

当前已经具备：

- 多 Agent 发现与配置解析；
- Claude Code、Codex、CC Switch、OpenCode、Gemini CLI、OpenClaw 风险扫描；
- Provider、base URL、本地代理与真实上游链路识别；
- 明文密钥、危险权限、MCP、敏感文件和跨 Agent 集中风险检查；
- HTML / JSON 报告；
- 部分 Agent 的 baseline、dry-run、backup、apply、restore；
- Codex、CC Switch 等不可自动整改项的手工整改指引；
- Electron 桌面预览壳和未签名 macOS 打包能力。

因此，当前阶段正式定义为：

> **0.0.5 安全加固 + 双端小范围 Pilot + CLI / macOS Desktop 联合公开发布准备。**

## 2. 当前唯一主线

未来 6 至 8 周只围绕以下顺序推进：

1. 完成统一首次入口：一次完成发现、扫描、真实上游摘要、最重要的 3 至 5 个行动和下一条命令；
2. 完成风险处置语义：区分“接受当前任务”“信任自建/内部端点”“项目级忽略”，并保留可验证、可撤销的本机审计；
3. 在同一个 core 和行动任务 schema 上完善 macOS Desktop，不复制 CLI 规则或另建状态模型；
4. 邀请 5 至 10 名真实用户分别验证 CLI 与桌面版的“发现 → 修复或接受 → verify/复扫确认”闭环；
5. 完成 Git 历史清理、独立敏感信息复核、macOS 签名与公证、CLI 安装矩阵和桌面安装验证；
6. 第一次对外发布同时提供 npm CLI 与 macOS Desktop，不单独提前公开其中一个入口；
7. 用真实下载、扫描和复用行为扩大到 20 人验证强需求，再决定 Team、Enterprise 和运行时能力。

不得同时展开团队管理后台、企业多租户、SIEM / DLP / IAM 集成或运行时拦截。

## 3. 用户购买理由

AgentGuard 首先回答三个问题：

1. **我的机器上装了哪些 AI Coding Agent？**
2. **我的代码和上下文最终发给了谁？**
3. **这些 Agent 当前能够读取什么、执行什么？**

当前推荐的用户表达：

> **看清你的 AI Coding Agent 正在连接谁、读取什么、执行什么。**

技术定位“多 Agent、多模型、多 Provider 的安全配置中心”继续保留，但不作为面向普通用户的第一句解释。

## 4. CLI 产品原则

### 4.1 首次体验

新用户不应先学习多个子命令。默认入口应逐步统一为：

```bash
agentguard
# 或
agentguard scan
```

一次完成环境发现、配置扫描、风险摘要、链路说明和下一步建议。

### 4.2 风险价值排序

优先强化以下高价值场景：

1. 本地代理背后的真实外部上游；
2. 未知 Provider / 中转 API；
3. 明文密钥、共享密钥与密钥散落；
4. bypass / YOLO / auto mode / 危险 Bash 权限；
5. MCP 文件、命令、数据库、浏览器访问范围；
6. OpenClaw 公网暴露；
7. 多 Agent 共用代理、密钥或未知上游形成的集中风险。

宁可规则少而准确，不得用大量低价值告警制造“看起来功能很多”的结果。

### 4.3 信任底线

- 默认只读；
- 本地运行；
- 不上传配置、代码和密钥；
- 输出必须脱敏；
- 自动修改必须先展示 diff；
- apply 必须备份；
- 必须可 restore；
- 未知 Provider 不武断判恶，允许用户确认 trusted / internal。

## 5. 桌面产品边界

桌面版不是另一个产品，也不重新实现扫描逻辑。桌面版必须复用 CLI / core。CLI 与桌面版是第一次
Public Preview 的两个正式入口，共用扫描结果、行动任务、可信来源、风险接受和验证语义。

Public Preview 第一阶段只提供：

- 开始扫描；
- Agent 配置地图；
- 最重要的 3 个风险；
- 风险详情和整改步骤；
- 导出 HTML / JSON 报告；
- baseline dry-run；
- 自动修复进入二级页面，必须展示 diff、备份和回滚信息。

第一阶段明确不做：

- 登录和账号体系；
- 云同步；
- 团队管理；
- 后台常驻监控；
- 实时阻断；
- 自动更新复杂策略；
- 企业控制台；
- 多租户。

## 6. 强需求验证标准

“用户觉得不错”不算验证。有效信号包括：

- 用户成功安装并完成首次扫描；
- 扫描发现了用户此前不知道的真实问题；
- 用户根据结果完成整改；
- 用户将报告发给同事或团队；
- 用户一周内再次运行；
- 用户主动要求支持更多 Agent、Provider 或持续检测；
- 用户提交 Issue、PR 或愿意试用下一版本。

当前关键指标：

- 安装完成率；
- 首次扫描成功率；
- 有效风险命中率；
- 二次使用率；
- 主动反馈率。

GitHub Star 只作为传播指标，不作为第一产品指标。

## 7. 决策优先级

出现需求冲突时按以下优先级判断：

1. 是否提高首次安装和首次扫描成功率；
2. 是否让用户发现此前不知道的真实风险；
3. 是否降低误报并提升解释性；
4. 是否增强用户对本地、只读、脱敏和可回滚的信任；
5. 是否提升桌面版易用性；
6. 其他团队和企业扩展能力。

## 8. 变更控制

任何与本文件相冲突的旧 PRD、路线图、发布决策和设计说明，均以本文件和 `docs/DEVELOPMENT_PLAN.md` 为准。

当前发布决策为“先完成首次入口与风险处置语义，再开发 macOS Desktop，CLI 与桌面版联合公开发布”。
若要改变此顺序或拆分两个发布入口，必须先更新本文件并记录决策原因，不能只在代码提交或聊天中改变方向。
