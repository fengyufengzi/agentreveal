## 1. 背景与问题

当前 HTML 报告能够发现并展示 Agent、Provider、MCP、凭证、权限和代理链路风险，但用户仍需自行回答：

1. 哪些项目必须马上处理？
2. 哪些项目只是需要确认，而不是漏洞？
3. 哪些预期配置可以接受或仅作为观察信息？
4. 应该如何整改，整改完成后如何确认成功？

当前实现包含约 63 条具体规则，绝大多数规则有一句建议，但只有少量规则提供分步整改，且规则声明的
`fixable` 与现有 baseline 实际能力没有形成可靠映射。报告仍以严重度和 Agent 为主要组织方式，无法直接
形成行动优先级。

因此，本轮不扩展 Agent 数量，不建设 Dashboard，不进入 Runtime Enforcement。先补齐：

```text
发现 → 判断 → 行动 → 验证
```

## 2. 产品原则

### 2.1 严重度不等于行动优先级

- `severity` 表示潜在影响。
- `priority` 表示用户应该多快处理。
- 优先级同时考虑暴露面、证据可信度、影响范围、是否正在生效以及整改成本。

例如，公网明文 HTTP 即使当前规则为中危，也应进入优先处理；已知本地代理即使涉及敏感流量，确认归属
后可以作为观察项。

### 2.2 每条发现必须落入一种处置类型

| 类型 | 含义 | 用户动作 |
|---|---|---|
| `fix` | 已有足够证据，应整改 | 自动修复、引导修复或手动修复 |
| `review` | 是否构成风险取决于用户上下文 | 确认归属、用途、暴露范围或信任关系 |
| `cleanup` | 不紧急，但应缩小长期暴露面 | 清理闲置配置、凭证或权限 |
| `observe` | 配置事实或系统状态，不形成默认待办 | 确认后保留观察 |

### 2.3 报告先展示行动，再展示证据

报告首页顺序调整为：

1. 立即处理。
2. 需要确认。
3. 建议清理。
4. 配置观察。
5. 按 Agent 查看完整证据。

### 2.4 不以“自动修改更多文件”为成功标准

自动修复只覆盖已有安全写入、备份和回滚保障的配置。其余发现必须给出具体手动步骤和验证方法，不能
为了提高自动修复率而扩大写入风险。

## 3. 本轮范围

### 3.1 规则处置矩阵

为 63 条具体规则建立机器可读矩阵，至少包含：

- 处置类型：`fix | review | cleanup | observe`
- 行动优先级：`P0 | P1 | P2 | P3`
- 判断可信度：`high | medium | low`
- 修复方式：`baseline | guided | manual | none`
- baseline 对风险的效果：`resolve | mitigate`
- 为什么要这样处理
- 用户下一步
- 整改后的验证方法
- 可以接受该风险的条件
- 根因分组键

扫描器内部的通用 `DEEPSCAN_FAILED` 作为系统健康事件单独处理，不计入 63 条安全与兼容规则。

### 3.2 下一步行动报告

HTML 报告新增：

- 顶部行动摘要与数量。
- 按 `P0 → P3` 排序的行动队列。
- “立即修复 / 需要确认 / 建议清理 / 配置观察”分区。
- 每项的行动理由、下一步、验证方法和修复方式。
- 自动修复项显示 `baseline --dry-run` 与带备份的 apply 提示。
- 原有 Agent 视图和严重度过滤继续保留，保证证据可追溯。

### 3.3 根因聚合

本轮先提供稳定的 `group` 元数据和分组展示，不删除原始 finding。典型分组包括：

- 同一 Provider 的未知端点与非 TLS。
- 同一 MCP 的远程执行与内嵌凭证。
- 同一代理链路产生的本地端点、代理开启与跨 Agent 集中点。
- 同一凭证产生的明文存储与跨 Agent 复用。

JSON 仍保留全部 finding，避免破坏现有消费者；HTML 可以提示同组项，后续版本再引入稳定的实例指纹和
持久化处置状态。

## 4. 多人并行开发拆分

| 工作流 | 交付物 | 边界 |
|---|---|---|
| 规则审计 A | Claude Code、Codex、CC Switch 规则分类 | 不改报告渲染 |
| 规则审计 B | OpenCode、Gemini、OpenClaw、Workspace 规则分类 | 不改报告渲染 |
| 报告设计 | 信息架构、兼容方案、测试清单 | 不改规则判断逻辑 |
| 主线集成 | 机器可读矩阵、扫描结果 enrichment、HTML 与文档 | 统一类型和最终合并 |

共享类型、规则矩阵主文件和 HTML 渲染器由主线统一修改，避免并行编辑冲突。

## 5. 实施顺序

### M1：规则矩阵

1. 准确枚举 63 条规则和通用系统健康事件。
2. 完成处置类型、优先级、修复方式和验证方法。
3. 建立覆盖测试，新增规则未进入矩阵时测试失败。
4. 对齐 baseline 已支持的自动整改能力。

### M2：扫描结果 enrichment

1. 保留现有字段和输出结构。
2. 为每条 finding 附加 `action` 元数据。
3. 对未识别规则提供保守的 `review/P2/guided` 回退值。
4. 保持输出契约 `schemaVersion: 1`，只增加可选字段。

### M3：下一步行动报告

1. 顶部输出最重要的三到五项行动。
2. 按处置类型和优先级生成完整行动区。
3. 观察项不再使用“待修漏洞”的措辞。
4. 保留原始证据、Agent 总览和严重度过滤。
5. 所有动态内容继续执行 HTML 转义，保持报告离线、自包含。

### M4：验证与 Pilot

1. 单元测试覆盖矩阵、排序、分区、自动修复提示和 XSS。
2. 使用现有真实报告验证 21 项发现的行动分类。
3. 执行完整测试和 npm 打包检查。
4. 由 5–10 名用户重新试用，并回收结构化反馈。

## 6. 验收标准

- 63 条具体规则全部存在处置矩阵条目。
- 通用扫描失败事件有保守处置方式，但不混入安全规则总数。
- 每条报告发现都有处置类型、优先级、下一步和验证方法。
- baseline 已覆盖的规则显示为 `baseline`，并区分完整解决与风险缓解；其他规则不得误称可自动修复。
- HTML 首页能在不展开证据的情况下回答“先做什么”。
- `observe` 项不进入立即处理数量。
- 原有 JSON 顶层结构、CLI 退出码和严重度语义不破坏。
- 报告中的标题、证据、行动和验证内容全部经过 HTML 转义。
- 完整测试通过，且不发生敏感信息明文输出。

## 7. 本轮暂不实现

- Dashboard、多用户和服务端存储。
- 跨机器 Inventory。
- Runtime Tool Call Enforcement。
- AI 自动判断端点是否可信。
- 持久化的接受风险、误报、负责人和到期时间。
- 直接从 HTML 修改本地配置。

这些能力放到下一阶段的 Triage State 与 Drift Tracking，前提是 Pilot 证明“行动报告”能够显著提高实际
整改率和重复使用意愿。
