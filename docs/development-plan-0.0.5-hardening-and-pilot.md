# AgentGuard 0.0.5 处置语义加固与 Pilot 计划

> 状态：代码级 P0、GitHub Pre-release 和资产回装验证已完成；可开始 5–10 人 Pilot。
>
> 目标：修复风险接受作用域和聚合任务语义，再用真实用户验证修复/接受/复扫闭环。

## 1. 为什么不能直接发布当前候选

当前跨平台修复指引和风险接受已经可用，审查最初发现两个会影响安全结论的问题：

1. **已解决**：acceptance schema v2 现按规范化 cwd 的 SHA-256 `scopeId` 隔离；旧 v1 记录为 legacy，
   不再影响任何项目。
2. **已解决**：聚合任务现在按规则保存和展示全部下一步、验证与接受条件；同一任务包含“未知端点 + 明文 HTTP”时，
   两项条件都会进入报告、接受前确认、审计摘要和单任务验证。

`0.0.5-pilot.1` 已从 GitHub Release 资产完成校验、干净安装和隔离环境报告验证，
现在只向 5–10 名受邀用户分发；Pilot 期间不继续开发 Dashboard、Drift 或自动凭证迁移。

## 2. P0：风险接受作用域

> 状态：已完成。实现与回归覆盖 acceptance schema v2、legacy v1、跨项目退出码、符号链接、相对路径、
> 尾部斜杠和大小写文件系统语义。

### 2.1 默认行为

- 接受记录按 `taskId + scopeId` 匹配。
- 第一版默认使用当前项目作用域，`scopeId` 由规范化 cwd 的 SHA-256 计算，不明文持久化完整项目路径。
- HTML、CLI 和 `risk list` 明确显示“当前项目”。
- 在未实现安全的全局作用域前，不允许一个项目的接受记录自动应用到其它项目。

### 2.2 存储升级

- acceptance schema 升级并保留 reason、createdAt、expiresAt、revokedAt 和任务摘要。
- 旧的无作用域记录不能静默作为全局记录继续生效；应标记为 legacy/inactive，要求用户重新确认。
- 文件继续使用 0700 目录、0600 文件、原子写入和完整历史。

### 2.3 验收

- 两个临时项目都有 `.env` 时，在项目 A 接受后，项目 B 仍显示风险并保持正确退出码。
- 同一项目重新扫描时接受状态稳定。
- 大小写、符号链接、相对路径和尾部斜杠规范化有测试覆盖。
- 审计文件不包含 secret；scope hash 不被当作可逆项目标识展示。

## 3. P0：聚合任务完整处置语义

> 状态：已完成。`ActionTask.requirements` 是报告、接受、审计和验证共用的规则级真源。

### 3.1 报告

- 任务卡合并展示所有子规则的去重下一步、验证方法和接受条件。
- 每个条件保留规则 ID，用户知道一项操作解决了哪些规则、还剩哪些条件。
- 明确标注修复命令是完整解决、风险缓解还是辅助步骤。

### 3.2 接受前确认

- `risk accept` 在写入前列出将被隐藏的全部规则、严重度和接受条件。
- 接受记录保存完整规则摘要，但不保存 evidence 或内部端点。
- P0 继续强制到期；P1/Review 默认建议设置复审时间。
- 不允许把报告占位文本“说明接受原因”直接作为真实 reason。

### 3.3 验收

- unknown endpoint 与 insecure HTTP 聚合后，两项的处置和接受条件均可见。
- 接受聚合任务后，审计摘要包含所有关联规则。
- 任一子规则的 P0/高危、限时条件和不完整修复状态不会被 primary 文案覆盖。

## 4. P0 发布 blocker：单任务验证闭环

> 状态：已完成。报告生成时保存不含 evidence、路径、动态标题或端点的项目级规则快照。

新增：

```bash
agentguard risk verify task-xxxxxxxxxxxx
```

输出至少区分：

- 已解决：当前扫描不再存在该任务。
- 仍存在：列出剩余关联规则。
- 已缓解：部分规则消失，但任务仍存在。
- 已接受：显示作用域和到期时间。
- 已过期/已撤销：重新进入待办。
- 身份变化：规则仍可能存在，但 task ID 因配置对象变化而改变。

HTML 必须明确：报告是静态快照，执行命令后需要重新扫描并重新生成报告。

实现结果：`risk verify` 对未解决状态使用退出码 2，对已解决和当前有效接受使用退出码 0；
部分规则消失但同一任务仍存在时输出“已缓解”，同族同规则迁移到新实例时提示身份变化和候选新 task ID；
没有报告快照或接受历史时使用退出码 1 返回“无法确认”，不猜测已解决。

## 5. P1：Pilot 文档与发布

### 5.1 发布前

- 同步 README、当前产品能力、quickstart、feedback、Changelog 和 Release Notes。
- 所有安装命令统一到同一个 `0.0.5-pilot.N` tag/tarball。
- 完成 npm pack、SHA-256、干净前缀安装和真实报告验证。
- 使用两个不同 cwd 验证 acceptance scope。
- 静态 HTML 继续只读；不增加本地执行桥接。

### 5.2 7–14 天 Pilot

范围：5–10 名多 Agent 用户，不新增 Agent 和规则数量；至少 3 名使用签名、公证 DMG 且全程不使用
AgentGuard CLI，至少 2 名使用 CLI。

成功指标：

- 安装成功率至少 90%；CLI cohort 首次 `doctor → report` 中位不超过 10 分钟。
- Desktop cohort 至少 80% 能独立理解项目选择并完成首次扫描，项目扫描不得请求无关受保护目录权限。
- 至少 2 名 Desktop 用户成功导出并重新打开 HTML 报告。
- 至少 80% 用户能在 3 分钟内指出最先处理的任务。
- 至少 60% 用户能独立复制并执行一条本机修复命令。
- 至少 3 人执行真实处置，其中至少 2 人通过 verify/复扫确认结果。
- 至少完成 3 次 `accept → list → verify/revoke/expiry` 闭环。
- 至少 3 人发现此前不知道的真实问题，至少 1 个团队愿意复跑或接入 CI。
- 0 次明文泄漏、配置损坏、无法恢复、跨项目错误隐藏和关联规则误接受。

未达到指标时只修安装、规则、任务身份和文案，不进入下一大模块。

## 6. Pilot 通过后的推荐顺序

1. Endpoint trust 和项目级低优先级规则忽略已经完成；先在 Pilot 中验证用户能否正确区分 accept、trust
   与 ignore，任何错误隐藏都先修规则与处置语义。
2. Pilot 通过后再做 Drift Tracking：本地快照、new/resolved/unchanged/regressed/acceptance-expired，只对新增 P0/P1 做 CI 门禁。
3. Secret Plan：根据 Pilot 中凭证迁移阻塞比例决定是否提前；先做只读 plan，再有限支持 Codex keyring 和
   Claude helper，CC Switch 永远保持原应用人工修改。
4. 桌面端操作按钮：等 CLI 状态机稳定后再做 typed IPC、确认、执行和验证；静态 HTML 永远只读。

如果至少 40% Pilot 用户把“不会或不敢迁移凭证”列为最大阻塞，可把只读 `secret plan` 提到 Drift 前；
完整 migrate 不随 plan 自动提级。
